# 部署与运维

本仓库提供源码和自行构建脚本，不提供官方安装包。部署前阅读 README 的[兼容与已知限制](../README.md#兼容与已知限制)。以下路径和配置均为示例。

## 目录与配置

程序根与数据根必须是彼此独立、互不包含的本机绝对目录，不能是磁盘根；发布包、两根目录及现有父目录不能是重解析点。

| 位置 | 用途与权限 |
|---|---|
| `C:\Program Files\DbBackupManager` | 程序根，版本存入 `versions`；服务身份只读、执行，已有版本不覆盖 |
| `C:\ProgramData\DbBackupManager\config` | 外部配置 `web.json`、`worker.json`，仅相应身份访问 |
| 数据根下 `keys\cookie` | Web 专用 Cookie Key Ring，Worker 不得访问 |
| 数据根下 `keys\business` | Web 与 Worker 共享的业务凭据 Key Ring |
| 数据根下 `logs\web`、`logs\worker` | 分离日志，不记录秘密或完整连接信息 |

服务通过 `--DbBackupManager:ExternalConfigurationPath=绝对路径` 读取外部 JSON。文件必须在程序发布目录外且不是重解析点；缺失、无权限或 JSON 无效时启动失败。配置只在启动时读取，修改后重启相应服务。

`web.json` 结构如下，占位符必须替换，真实配置不得提交仓库、Issue、日志或截图：

```json
{
  "Urls": "http://127.0.0.1:5080",
  "ConnectionStrings": {
    "PlatformDatabase": "[REDACTED_SECRET]"
  },
  "DataProtection": {
    "CookieKeyRingPath": "[ABSOLUTE_PROTECTED_COOKIE_KEY_DIRECTORY]",
    "BusinessCredentialKeyRingPath": "[ABSOLUTE_PROTECTED_BUSINESS_KEY_DIRECTORY]"
  }
}
```

`worker.json` 使用同一平台连接及业务 Key Ring，省略 `Urls` 和 `CookieKeyRingPath`。管理员须事先创建受保护配置和密钥目录；业务 Key Ring 必须有 Web 生成、Worker 可读取的有效密钥，不能用伪造文件绕过启动检查。

### 差异备份验收放行

统一计划的 SQL 执行端口支持普通 FULL、DIFFERENTIAL 和临时 COPY_ONLY FULL；当前旧策略与 Worker 仍只执行原有 FULL 路径，配置此项不会启用计划调度或页面入口。DIFF 的内置已验收版本清单目前为空，不继承 FULL 的兼容结论。

仅在专用验收环境中，可向 `worker.json` 添加显式放行项，为后续计划接入与人工还原验收做准备：

```json
{
  "TargetSql": {
    "DifferentialBackupAcceptance": {
      "Overrides": [
        {
          "Version": "15.0",
          "Reason": "专用隔离环境验证 FULL 与 DIFF 及实际还原"
        }
      ]
    }
  }
}
```

版本键仅为产品主次版本号，例如 `10.50`、`15.0`、`16.0`，不包含补丁号、Edition 或驱动版本。原因必须非空、最多 500 字且无控制字符；原因不能包含凭据、真实服务器地址或业务数据。配置错误或重复版本会阻止适配器注册。每次使用配置放行时，日志记录警告事件 6101、版本键和原因。修改后需重启 Worker；验收结束删除该例外并重启。

没有内置验收记录且没有有效配置放行的 DIFF，在发出 BACKUP 前以 `BackupTypeNotValidated` 明确失败，不进入 NeedsAttention、不自动重试，也不降级成 FULL。压缩能力和旧 SQL/TLS 前提仍按现有规则校验，放行不能绕过它们。LocalDB 命令测试和 VERIFYONLY 不代表目标版本的真实恢复验收；人工验收通过后再登记内置版本清单。

计划任务接入后使用 v3 路径规则：`full/` 下分别为 `{UTC时间}_{AttemptId}_FULL.bak` 和 `_COPYONLY.bak`，`diff/` 下为 `_DIFF.bak`；旧策略保持 v2 命名。任务专属文件已存在时拒绝执行；远端仍通过 `.part` 文件检查后重命名，禁止覆盖。文件名用于识别用途，实际差异基线以 SQL 元数据核对结果为准。

Production Web 使用 HTTP，登录密码、Cookie 和业务内容没有传输加密。须用防火墙及网络 ACL 限制可信来源，禁止直接暴露公网。Cookie、CSRF、授权、锁定、限流和密钥隔离仍然启用。

### 备份元数据核对权限与失败表现

只读元数据端口读取 Attempt 专属文件的 `RESTORE HEADERONLY`、`msdb` 历史及当前数据库的数据文件基线，尚未接入 Worker 自动执行。读取账号须能连接 `master`、`msdb` 和指定目标数据库；由 SQL Server 服务身份读取备份文件，因此文件 ACL 也必须允许该服务身份读取。

`HEADERONLY` 要求 `master` 中的 `CREATE DATABASE` 权限；仅有 `db_backupoperator` 不满足此要求。该权限同时可使账号看到 `sys.database_recovery_status` 的目标行。它具有创建数据库的能力，管理员应在精确目标评估并单独授予；本功能不要求默认加入 `sysadmin`、`dbcreator` 或授予 `ALTER ANY DATABASE`。权限不足时保留 SQL 成功事实，核对标 `Unknown / baseline.permission_denied`，不显示整体健康。依据见微软的 [备份头权限](https://learn.microsoft.com/en-us/sql/t-sql/statements/restore-statements-headeronly-transact-sql#permissions) 与 [恢复状态可见性](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-database-recovery-status-transact-sql)。

历史查询实际需要 `msdb.dbo.backupset`、`msdb.dbo.backupmediafamily` 和 `msdb.dbo.backupmediaset` 的 `SELECT` 权限；已有有效读取权限时无需重复授予，否则只授予这些对象，不授予整个 `msdb` 的读写权限。目标库的 `sys.database_files` 使用 `public` 的目录读取权限及目标库连接权限，仍受元数据可见性限制，见 [数据文件目录权限](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-database-files-transact-sql#permissions)。没有可见记录与被明确拒绝权限分别返回“历史不存在／缺字段”和“权限不足”，均不推断健康。

头部与历史由专属路径独立定位；零条、多条、缺列、NULL、读取取消与超时分别返回结构化原因，多条不能默认选第一条。已确认字段矛盾时追加原始最小证据并标 `Mismatch / baseline.source_conflict`。核对只登记原 Attempt，不能重新 BACKUP、创建 Attempt 或触发重试。提交响应丢失时，以原 `MutationId` 重放固定登记命令；进程恢复后可从已提交证据重建命令，不重新读取变化后的活动基线。重放返回原观察的活动结论与时间，不替代执行前复查；新的核对观察使用新的 `MutationId`。

完成 UTC 优先取平台已观察的 SQL 完成事实，SQL 开始、结束时间另存未指定时区的原值。服务器偏移来自 `SYSDATETIMEOFFSET()`；SQL Server 2022（16.x）及以上才读取 [CURRENT_TIMEZONE_ID](https://learn.microsoft.com/en-us/sql/t-sql/functions/current-timezone-id-transact-sql) 并解析明确的时区规则。旧版本、未知 ID 或读取失败保持时区未知，不用 Worker 本机时区替代；恢复登记缺少可靠换算依据时 `CompletedAtUtc` 留空，继续受保留保护。读取支持不等于目标版本放行；LocalDB 测试不替代真实目标版本与隔离还原验收。

## 构建发布目录

预先创建绝对输出根。发布脚本默认 `Plan`，只输出计划；确认后显式执行 `Publish`：

```powershell
$packageRoot = 'D:\DbBackupManager-Releases'
pwsh -NoProfile -File .\scripts\部署\Publish-DbBackupManager.ps1 `
  -Command Plan -Version 1.0.0-preview.1 -OutputRoot $packageRoot
pwsh -NoProfile -File .\scripts\部署\Publish-DbBackupManager.ps1 `
  -Command Publish -Version 1.0.0-preview.1 -OutputRoot $packageRoot
```

| `-DeploymentMode` | 目录后缀 | 服务器前提 |
|---|---|---|
| `SelfContained`（默认） | `-win-x64` | 包内携带运行时，无需预装共享运行时 |
| `FrameworkDependent` | `-win-x64-framework-dependent` | 机器级 Windows x64 .NET 10.0 与 ASP.NET Core 10.0 稳定运行时，基础 .NET 补丁不低于选中的 ASP.NET Core 补丁 |

轻量模式在上述两条命令均添加 `-DeploymentMode FrameworkDependent`。它按机器级安装查找运行时，仅在 10.0 系列内选择稳定补丁，不接受仅有其他主/次版本或预览版的服务器；脚本不安装运行时。两种模式均不裁剪或手工删 DLL。

产物记录完整来源 Git SHA，包含 Web、Worker、逐文件长度和 SHA-256 清单、项目 LICENSE、第三方许可/NOTICE 及索引。脚本拒绝覆盖同版本目录；失败暂存目录保留供检查。新清单为 schemaVersion 2，当前部署脚本兼容旧版 1 自包含包，旧部署脚本不能部署新版清单。

普通 `Publish` 可生成隔离验收包，不表示获准公开分发。对外分发须使用 `-ForDistribution`：要求工作树干净，许可、署名及独立条款检查通过。当前 SNI 审查记录仍为 `approved=false`，该入口受阻；安装时接受条款不能代替发布审查。详细条件见[二进制第三方条款](../DISTRIBUTION-TERMS.md)，不得直接上传普通验收包绕过门禁。第三方许可材料和静态图标来源须随包保留。

## 安装服务

先用独立部署身份在专用平台库手动应用已审查的 Migration，见[开发运行](开发运行.md#配置与首次启动)。Web/Worker 启动和部署脚本均不会自动迁移数据库；运行账号只授予业务所需数据权限。

部署脚本无 `-Apply` 时只校验并输出计划。先检查包、目录、配置、密钥和 Plan 返回的条款：

```powershell
$package = 'D:\DbBackupManager-Releases\DbBackupManager-1.0.0-preview.1-win-x64'
$program = 'C:\Program Files\DbBackupManager'
$data = 'C:\ProgramData\DbBackupManager'
pwsh -NoProfile -File .\scripts\部署\Invoke-DbBackupManagerServiceDeployment.ps1 `
  -Action Install -PackageRoot $package -InstallRoot $program -DataRoot $data
```

安装和升级先核对清单、全部文件、运行时配置及轻量包所需共享框架；缺失、未登记文件、重解析点或哈希不符均拒绝。前置检查失败不会复制文件、修改 ACL、创建或停止服务。

执行安装须用提升权限的 PowerShell，加上精确确认短语。含条款标记的新包须由有权代表使用主体的执行者阅读包内条款和完整 SNI 许可后加 `-AcceptDistributionTerms`：

```powershell
pwsh -NoProfile -File .\scripts\部署\Invoke-DbBackupManagerServiceDeployment.ps1 `
  -Action Install -PackageRoot $package -InstallRoot $program -DataRoot $data `
  -AcceptDistributionTerms -Apply -Confirmation 'Install DbBackupManager.Web DbBackupManager.Worker'
```

脚本复制到新版本目录，创建 `DbBackupManager.Web`、`DbBackupManager.Worker` 两个自动服务，使用对应 `NT SERVICE\服务名` 虚拟账号，设置 Production、外部配置参数和目录 ACL，注册 Windows Application 事件源后启动。连接秘密不会写入服务命令行。同名事件源若属于其他日志则拒绝；创建服务后失败会尝试清除本轮服务记录，保留版本目录。

平台库仅允许 Windows 身份验证时，首次安装使用 `-Stage`，先创建手动服务并设置 ACL，暂不启动（只适用于 Install）：

```powershell
pwsh -NoProfile -File .\scripts\部署\Invoke-DbBackupManagerServiceDeployment.ps1 `
  -Action Install -PackageRoot $package -InstallRoot $program -DataRoot $data `
  -Stage -AcceptDistributionTerms -Apply -Confirmation 'Install DbBackupManager.Web DbBackupManager.Worker'
```

随后由部署身份在精确平台库为两个服务账号配置适用的登录、用户和最小数据读写权限，不授予 sysadmin。核对配置、有效业务密钥及实际程序文件的读取/执行 ACL 后，将服务设为自动并依次启动 Web、Worker。预检通过不代表数据库权限或服务身份启动验收已通过。

## 升级、卸载与恢复

备份集迁移按初始架构、`AddBackupPlans`、`AddBackupSets` 的顺序应用，停服、备份平台库后再迁移。它新增逻辑备份集 `BackupSets`、只追加的 `BackupSetEvidence`，以及物理副本的可空 `BackupFiles.BackupSetId`；旧副本不自动补关联。新文件登记必须先登记本 Attempt 的备份集，关联失败时中止登记，不能落成未关联的新副本。

`BackupSets` 或 `BackupSetEvidence` 已有任何数据时，`AddBackupSets.Down` 会在删除表、列或外键之前中止。无数据时才可以退回 `AddBackupPlans` 并重新升级。已有登记或核对证据时应从迁移前的平台库备份恢复，不能绕过守卫删表。

任务身份迁移 `AddBackupTaskPlanIdentity` 在 `AddBackupSets` 之后应用，仍须停止 Worker、备份平台库后迁移，再启动 Web 和 Worker。任务身份在旧策略与计划版本之间二选一；计划版本使用复合外键，任务类型与用途快照在写入边界核对。既有任务保留策略身份、FULL 类型、原 COPY_ONLY 开关和 v2 路径；用途为空，不自动推断或转换为计划任务。计划快照显式选用 v3，LOG 仅预留持久化类型，不代表可以执行。

本次迁移不启用计划调度或执行，旧领取入口只领取旧策略任务。尚无计划任务及用途快照时，可回退到 `AddBackupSets`，旧策略任务和快照保留；已有计划任务、用途快照或非 FULL 任务时，`Down` 在修改任何列、索引和外键之前中止，应从迁移前的平台库备份恢复。计划调度、基线门禁和删除保护仍需后续接入验收。

元数据值旁保存 `Known`、`Unknown` 或 `NotApplicable` 状态；FULL 的差异基线为不适用。核对不可用或冲突不表示备份健康，也不撤销已观察到的 SQL 成功事实。完成 UTC 时间保存来源和 `completion.*` 原因码；SQL 原始本地时间单独保存。完成时间未知属于保守保护条件，启用计划文件清理时必须结合备份集元数据判断；此次迁移只提供持久化，不启用计划执行或清理。核对证据仅包含身份、LSN、恢复分支、类型、标志和时间，不保存备份头中的用户名、服务器名或描述文本。

维护前停止提交新操作，检查活动任务、租约、Worker 心跳和积压，备份平台库、外部配置及两套 Key Ring。涉及 Migration 时先审查差异，用独立部署身份在维护窗口执行，运行账号不承担迁移。应用备份计划表迁移时，先停止 Worker，完成迁移后再启动 Web 和 Worker。`BackupPlans` 尚无数据时可以 `Down` 回退该迁移；已有计划行时 `Down` 会中止并提示从平台库备份恢复，不能只退回二进制。

| 操作 | 参数与行为 |
|---|---|
| 升级 | 使用 `-Action Upgrade`、新 `-PackageRoot`、原程序/数据根；先 Plan，再加 `-Apply`、必要的条款接受和确认短语 `Upgrade DbBackupManager.Web DbBackupManager.Worker` |
| 卸载 | 使用 `-Action Uninstall`、原程序/数据根，无需发布包；先 Plan，再加 `-Apply` 和确认短语 `Uninstall DbBackupManager.Web DbBackupManager.Worker` |

升级要求两个服务已存在且可执行文件位于指定程序根。先复制校验新版本，再停服、切换路径并启动；切换或启动失败尝试恢复旧路径并启动，保留新目录。此回退不恢复数据库或机器共享运行时，旧轻量版本仍需要配套运行时。

卸载只停止和删除经归属检查的两个服务记录，保留程序、数据、密钥、事件源、日志及平台库。不要把程序升级或卸载当作数据清理。

灾难恢复时，在独立目标恢复平台库及同一时间点的外部配置、两套密钥，重新核对服务用户映射、ACL、连接和密钥路径。启动恢复 Worker 前隔离不应访问的源、策略、存储、SMTP 和 Retention；仅停用计划不能阻止所有后台 I/O。保留原环境和恢复材料，验证数据、凭据解密、会话、心跳及精确目标连接后再切换。平台库恢复不会自动搬迁备份文件；VERIFYONLY 也不能代替业务库的隔离还原验证。

## 运行检查与停服

- `/health/live` 仅表示 Web 可响应；`/health/ready` 反映 Web 最近一次平台库 `SELECT 1` 探测，失败或未探测返回 503，成功返回 200。它不检查 Migration、表权限、密钥、Worker、目标 SQL 或存储，也不保证下一次业务操作成功。
- 两个进程各自等待平台连接就绪后开始后台轮次，连接恢复后按原业务规则继续，不自动重发结果不确定的 BACKUP。已经开始的轮次仍遵循原异常、租约和恢复规则。
- Windows Application 日志中，Event ID 6001 表示平台连接不可用，持续故障每 5 分钟提醒；6002 表示首次通过或恢复。两个服务名对应的事件源由部署管理员注册，服务身份不能替代首次登记。
- Web 停服时给每条连接 5 秒完成在途响应，之后中止残留连接。这是连接排空时限，不是整个服务停服时限，也不改变独立 Worker 的任务语义。重新连接后查询任务状态，避免因响应丢失重复提交备份。
- 首次部署及运行时、权限、配置或目标版本变更后，在专用目标核对连接、备份、文件校验和隔离还原，再启用业务计划。自动化测试不能代替部署环境验收。

部署脚本的本地回归命令见[开发运行](开发运行.md#构建与测试)。
