# 架构说明

## 进程与分层

项目采用 .NET 10：Blazor Interactive Server、API 与认证位于同一个 Web 进程，独立 Worker 从 Platform DB 领取和执行后台任务。Web 离线不会阻止 Worker 工作，浏览器连接不是执行任务的前提。

| 项目 | 职责 |
|---|---|
| Domain | 业务模型、状态机与不变量，不依赖其他项目 |
| Application | 用例和端口，不依赖 ASP.NET Core、MudBlazor 或 EF Entity |
| Infrastructure | EF 持久化、SQL、文件存储、邮件与凭据保护 |
| Contracts | 公开 API 请求和响应类型 |
| Web | 页面、Controller、Cookie/CSRF、输入输出映射与事件 Relay |
| Worker | 调度、执行、恢复核对、Retention、通知及心跳循环 |

Blazor 直接调用 Application，不通过 HTTP 回调自身 API。Web 与 Worker 共用 Platform DB，但备份目标使用独立连接和适配器。部署为单 Web、单活动 Worker；多节点不在当前范围。

## 数据与凭据

Platform DB 最低 SQL Server 2019、兼容级别 150。只通过非池化 `IDbContextFactory` 创建短生命周期 Context；SQL Backup、SMB/SFTP 和 SMTP 等外部 I/O 期间不持有 Context 或数据库事务。

管理员、凭据、源服务器/实例/数据库、策略、任务/Attempt、文件副本、状态历史、审计、通知 Outbox、TaskEvent 和 Worker 心跳分别持久化。模型与 Migration 位于 Infrastructure；进程启动不会自动迁移。

Cookie 与业务凭据使用分开的 Data Protection Key Ring。业务密钥由 Web/Worker 共享，Cookie 密钥仅授予 Web；密文和密钥应随平台数据库按一致时间点保护与恢复，不能只备份数据库。

## 执行安全

任务保存不可变执行快照，Attempt 使用独立文件名与阶段事实。执行和核对通过租约、心跳与并发版本争用，失去提交资格的进程不能回写成功结果。

计划任务创建由 Application 区分管理员手动请求与内部时隙请求；只接受普通 FULL、DIFF 和手动 COPY_ONLY FULL，LOG 返回阶段未开放。手动请求必须指定当前计划版本，自动请求必须属于指定版本的有效 UTC 时隙；暂停计划阻止新的自动请求，管理员仍可手动创建。执行快照从平台配置及不可变计划版本组装，固定用途对应的类型、COPY_ONLY 和 v3 路径规则。

创建任务、快照、状态历史、审计及 TaskEvent 在同一短事务中提交。MutationId 绑定完整请求身份，重放不重建快照或追加记录；同槽竞争只保留一份任务，返回已有任务的请求也记录自己的幂等关联。后续配置修改不改变快照。创建成功仅表示 Pending 已入库，DIFF 的活动基线资格仍待执行接入核验；当前 Worker 继续只领取旧策略任务，计划创建不调用目标 SQL 或文件端口。

计划组合调度仅提供可显式调用的 `BackupPlanScheduler.RunOnceAsync`，尚未注册后台循环。每种类型只选择最近的到期时隙，按不可变版本的生效和结束边界计算；同刻或更晚的 FULL 取代旧 DIFF，明确失败的 FULL 才允许重新判断 DIFF。手动任务不作为定时时隙事实，已有任务不会自动重建或重试。

FULL 时隙成功须由同一 Attempt 的 SQL 成功、备份头与历史核对通过、本地校验成功共同证明，远端失败或远端阶段待核对不抹掉这三个事实；备份、本地校验待核对及缺失或冲突的事实保守视为不确定。当前 Attempt 尚不能证明成功时，只有全部 Attempt 均明确失败且无矛盾、核对通过或本地校验证据，才把 FULL 时隙判为失败；后续失败不能覆盖历史证据，Prepared 不作为明确失败依据。没有 Attempt 时也不能仅凭 Failed 放行 DIFF，只有明确的认领前准备失败历史才证明未执行。所有历史 FULL 处置均参与取代判断。每个计划在独立的短事务内锁定计划并串行化读取版本、暂停状态及任务事实，共用创建流程，整份决定原子提交；提交重放重新读取事实，不追加空转记录。配置无效只影响该计划，取消及平台库故障向上传递。该入口不读取活动基线、不连接目标 SQL、不访问文件，Worker 领取隔离继续保留。

执行阶段为 Backup、VerifyLocal、Transfer、ValidateCopy、Cleanup，按存储模式选择需要的阶段。调用 BACKUP 前准备目录并检查任务专属文件不存在；远程输出先写 `.part`，确认后在同目录重命名，拒绝覆盖。

SQL 调用后取消、失联或进程中断可能使结果不确定；此时保留 `NeedsAttention`，恢复只能读取证据，不能自动重发 BACKUP。管理员确认失败与显式重试是两个独立操作。Retention 只删除已登记到期文件，并维持至少一份保护底线。

## 状态与通知

状态、历史、审计和事件以短事务原子保存。TaskEvent 只携带失效提示，中央 Relay 发布后逐条确认；允许重复投递，页面重新查询当前事实。首次进入、重连和定期校准也会查询，不能依赖一条实时消息作为唯一状态来源。

Outbox 邮件采用至少一次投递。TaskEvent 默认保留已发布事件 30 天、最多 200,000 条；未发布事件受保护，状态历史独立保留。

## 安全边界

- 同源管理员 Cookie、CSRF、限流、安全戳复核与并发控制；API 使用稳定 Problem Details，不回显原始异常或秘密。
- SQL、SMB、SFTP 凭据加密保存；SFTP 必须核对 Host Key，路径访问限制在配置根内，拒绝路径越界及重解析跳转。
- Production HTTP、旧 SQL/TLS 与明文 SMTP 只在受控环境显式启用；已验证边界见[兼容与已知限制](../README.md#兼容与已知限制)。
- 认证、任意删除、结果不确定时重试和兼容范围的变化属于需要维护者审查的架构决策。

API 的完整字段及错误码以[OpenAPI](../src/DbBackupManager.Web/OpenApi/v1.json)为准，生成与验证方式见[开发运行](开发运行.md)。
